# تجربة LimeTorrents: Python مقابل Rust

التاريخ: 2026-10-17. البيئة: Windows 11 x64، معالج Intel Core Ultra 5 225H.

**النتيجة:** تحويل هذا المصدر إلى Rust مفيد لتقليل استهلاك المعالج والذاكرة. تحسن زمن البحث عبر الإنترنت كان صغيرا لأن انتظار الموقع والشبكة يمثل معظم الوقت. يبقى Python متاحا للتوافق مع إضافات البحث الأخرى؛ تحويل LimeTorrents وحده لا يغني عنه عند استخدام Torrents CSV.

## القياس المباشر

البحث عن `nirvana in fire`، خمس محاولات لكل تنفيذ. الأرقام التالية هي الوسيط، وليست أسرع محاولة.

| القياس | Python | Rust | الانخفاض |
|---|---:|---:|---:|
| الزمن الكلي | 2091 ms | 1980 ms | 5.3% |
| وقت المعالج المجمع | 296.9 ms | 109.4 ms | 63.2% |
| ذروة الذاكرة الخاصة المحجوزة فعليا، private committed | 26.40 MiB | 7.13 MiB | 73.0% |
| ذروة مجموع working sets، مأخوذة بالعينات | 70.77 MiB | 30.12 MiB | 57.4% |
| النتائج | 31 | 31 | متطابقة |

تراوح الزمن الكلي بين 1996–2148 ms لـPython وبين 1869–2005 ms لـRust. هذه عينة صغيرة على جهاز واحد وفي وقت واحد؛ نسبة تحسن زمن الإنترنت ليست ضمانا للأداء في كل شبكة أو مصدر. وقت المعالج هو زمن CPU، وليس نسبة استخدام المعالج.

`private committed` لا تعني حجم RAM المقيم. مجموع working sets أقرب لقياس الذاكرة المقيمة لكنه يتضمن صفحات مشتركة وقد يعدها أكثر من مرة، ويؤخذ كل 5 ms لذلك قد يفوّت قمما قصيرة. كلا القياسين يشمل عملية Rust وكل العمليات التابعة لها، بما فيها Python وعمليات console، ويستثني أداة القياس وخادم إعادة التشغيل.

## إعادة تشغيل HTML مسجل محليا

أعدنا تقديم صفحات حقيقية مسجلة من الموقع عبر HTTP على `127.0.0.1`، مع عشر محاولات لكل تنفيذ ولكل استعلام. يشمل الزمن تشغيل CLI والاتصال المحلي وتحليل النتائج؛ ليس قياسا للمحلل وحده.

| الاستعلام | النتائج / الصفحات المطلوبة | Python | Rust | التسارع |
|---|---:|---:|---:|---:|
| nirvana in fire | 31 / 2 | 294.5 ms | 87.2 ms | 3.38× |
| ubuntu | 160 / 4 | 353.0 ms | 108.4 ms | 3.26× |

انخفض وقت المعالج من 265.6 إلى 46.9 ms للاستعلام الأول، ومن 281.3 إلى 62.5 ms للثاني. انخفضت ذروة private committed من نحو 24.36 MiB إلى 5.47 و5.81 MiB على الترتيب.

## عدالة المقارنة والتحقق

- استُخدم نفس ملف Rust التنفيذي في جميع القياسات؛ الاختلاف هو اختيار `--limetorrents-backend python` أو `rust`. يستخدم تنفيذ Python بيئة CPython 3.14.8 المضمنة وإضافة LimeTorrents الأصلية 4.14.
- الترتيب يتناوب بين Python ثم Rust والعكس. استُبعد زوج إحماء لكل استعلام ولكل وضع: 50 تشغيلا مقاسا و6 تشغيلات إحماء مستبعدة.
- حدود البحث متساوية: مصدر LimeTorrents وحده، التصنيف `all`، حد 200 نتيجة، مهلة 20 ثانية. نجحت كل التشغيلات دون نتائج جزئية.
- تطابقت الروابط والعناوين والأحجام وعدد seeders وleechers في كل زوج من الأزواج الـ25 المقاسة. تطابقت أيضا العناوين الخام في تقارير إعادة التشغيل المحفوظة. قد تختلف التواريخ النسبية بثانية بسبب اختلاف وقت بدء التنفيذ.
- استُخدم Windows Job Object مع إدخال العملية قبل استئنافها لاحتساب CPU وذروة private committed لكل شجرة العمليات، حتى عند خروج Python قبل نهاية القياس.
- الصفحات المسجلة جُمعت بواسطة helper الأصلي، ولذلك كانت قد خضعت لفك الترميز وفك كيانات HTML مرة قبل حفظها. يتلقى التنفيذان نفس البايتات في إعادة التشغيل، ثم يجري كل منهما معالجته المعتادة. الاختبار المباشر يغطي الاستجابة الحقيقية أيضا.
- تطابق استخراج magnet من صفحة تفاصيل فعلية في التنفيذين، بما في ذلك infohash. نجح Rust مع مسار Python غير موجود، فلا يحتاج هذا المصدر إلى تشغيل Python عند اختياره صراحة.
- اكتشف اختبار التطابق الأول خمسة عناوين تحتوي محارف تحكم C1. أُصلح التنفيذ ليحفظ العنوان الخام وينظف عنوان العرض وفق سلوك المسار المشترك، مع اختبار انحدار. `parity-mismatch.json` تشخيص قديم قبل الإصلاح؛ نتائج `replay.json` و`live.json` لاحقة وتؤكد التطابق.
- بعد الدمج نجح `cargo test --locked`: 24 اختبارا، دون فشل، بما فيها اختبارات المصدر الجديد واختبارات البحث والتكامل الموجودة.

بسبب تطوير وحدات تحليل أخرى بالتزامن في مساحة العمل، جُمّدت نسخة البحث المستخدمة في القياس داخل `experiments/limetorrents-native`. التنفيذ الجديد مدمج أيضا في مصدر المشروع الرئيسي. اللقطة التجريبية تعزل المقارنة عن تغييرات تلك الوحدات.

SHA-256 للملف المقاس:

```text
58c443e4e7703548d5d20b1cba8606accaeaff7cf4aae7a0fa8f7fab5db2981f
```

المقابل: ارتفع حجم الملف التنفيذي المرصود من 1.97 MiB في حزمة Python السابقة إلى 5.95 MiB في التجربة، مع اعتماديات HTTP وHTML الجديدة. هذه أحجام ملفين مرصودين وليست عزلا لكل فرق في البناء. كما نتحمل صيانة محول Rust عند تغير الموقع.

## التشغيل

الحزمة المستقلة: `dist/torrent-search-limetorrents-comparison-20261017.zip`، حجمها 15.28 MiB، وتشمل بيئة Python للمقارنة. جرى فحص سلامة الملفات الأساسية داخل ZIP وتشغيل البحث من مجلد الحزمة في الوضعين؛ أعاد كل منهما 31 نتيجة كاملة. تقارير هذا الفحص في `packaged-rust.json` و`packaged-python.json`.

من مجلد الحزمة التجريبية بعد فك الضغط:

```powershell
.\torrent-search.exe --limetorrents-backend rust search "nirvana in fire" --source limetorrents
.\torrent-search.exe --limetorrents-backend python search "nirvana in fire" --source limetorrents
```

يبقى Python هو الخيار الافتراضي في هذه التجربة. لم نغيّر الافتراضي تلقائيا؛ يمكن اعتماد Rust لهذا المصدر بعد مراجعة النتيجة.

لإعادة بناء اللقطة من جذر المشروع:

```powershell
cargo test --manifest-path experiments/limetorrents-native/Cargo.toml --target-dir .cache/limetorrents-experiment-target --locked
cargo build --manifest-path experiments/limetorrents-native/Cargo.toml --target-dir .cache/limetorrents-experiment-target --release --locked
```

لإعادة القياس على Windows من جذر المشروع، مع Python محلي يحتوي `psutil` وبيئة Python المضمنة الموجودة في `.cache/python-3.14.8-embed-amd64`:

```powershell
python -B -X utf8 scripts/benchmark-limetorrents.py --mode replay --trials 10
python -B -X utf8 scripts/benchmark-limetorrents.py --mode live --trials 5
```

هذه الأوامر تستبدل تقارير القياس بنفس أسمائها؛ احتفظ بنسخة إذا أردت مقارنة قياس جديد بالسجل الحالي. الحزمة التجريبية لا تحتاج Python مثبتا على الجهاز، أما أداة القياس نفسها فتحتاج `psutil` وPython محليا.
